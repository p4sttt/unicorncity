## Goals

Стабильные, высокоуровневые цели (не меняются от этапа к этапу):

- **G1 — Токен-экономия.** Давать релевантный контекст нужного уровня абстракции, а не recall-dump.
- **G2 — Персистентность.** Память переживает сессии и изменения кода; не реконструируется с нуля.
- **G3 — Структурная навигация.** Отвечать на структурные вопросы (`dependents`, `blast_radius`, `data_flow`) за один запрос, а не grep-петлёй.
- **G4 — Переиспользование.** Успешные решения прошлых задач не решаются заново.
- **G5 — Мультиязычность.** Новый язык = новый провайдер при неизменном ядре (первый — Java).

## Инвариант архитектуры — training-free

**Решение принято:** HCM реализуется строго **training-free** — без дообучения, SFT или RL каких-либо
моделей. Вся ценность переносится через структуру и протокол MCP, а не через веса. Следствия,
обязательные для всех фич ниже (в т.ч. P1–P7):

- Ни одна фича не должна требовать обученного компонента. В частности **P3 (`explore(issue)`)**
  реализуется как детерминированная композиция запросов к графу + retrieval + память, а **не** как
  обученный explorer-субагент в духе [[fastcontext]] — заимствуется только его *инсайт* (offload +
  компактный контекст), но не механизм (обучение).
- Приоритет — приёмам, валидированным без обучения: структурный tool-интерфейс + reasoning-LLM +
  self-recovery ([[sherloc]]), структурный индекс как инструмент ([[code_isnt_memory_structural_index]]).
- Model-agnostic и обновляемость независимо от модели — прямые следствия этого инварианта.

Обоснование, что training-free маршрут достигает тех же результатов — в [[evidence]].

## Features — Built / в MVP

Сводка из репозитория (детали и статусы — `IMPLEMENTATION.md`); здесь без тех-подробностей.

**Готово:**
- Граф-индекс Java (tree-sitter → `FileIR` → `CodeGraph`), source roots, резолвер вызовов, Lombok.
- Запросы к графу: `interface`, `dependents`, `blast_radius` + рендер в компактный текст под бюджетом.
- Инкрементальное обновление по git-diff + property-тест «инкремент $\equiv$ ребилд».
- MCP-инструмент `query_graph`, E2E через `mcp.client` поверх stdio.

**Запланировано в MVP:**
- Семантический поиск по документации (прото-Level 2): `search_docs`, инкрементальный реиндекс.
- Память решений (Level 3): `save_solution` / `search_memory` / `prune`, survival-скоринг.
- Регистрация в Claude Code + dogfood-протокол (3 задачи $\times$ 2 прогона) — замер главного KPI.

## Features — Proposed (из литературы 2026)

Ещё **не** в тех-плане; каждая фича с обоснованием и статьёй-источником (подробно — [[evidence]]).

- **P1 — Line-range citations ($\to$ U1).** Ответы графа возвращают точные `(file, start, end)` диапазоны,
  а не только файл/FQN. Поле сходится на диапазоне строк как единице локализации:
  [[fastcontext]] (precise citation), [[sherloc]] (chunk-level span), [[swe_explore]] (line-level GT).
- **P2 — Гибридный retrieval поверх кода ($\to$ U2).** Добавить к call-graph семантический (vector) и
  лексический (BM25) индексы кода, слить в hybrid-ранжирование — три-компонентный индекс из
  [[code_isnt_memory_structural_index]] / [[codebase_memory_tree_sitter_kg]] ([[structural_codebase_index]]).
- **P3 — `explore(issue)` facade-инструмент ($\to$ U3).** Один вызов принимает NL-описание задачи и
  возвращает ранжированный region-список — по образцу exploration-субагента [[fastcontext]] (компактный
  контекст вместо оркестрации множества `query_graph` со стороны агента).
- **P4 — Диагностическая схема памяти ($\to$ U4).** Обогатить запись Level 3 5-польным finding из
  [[sherloc]]: *location explanation / root cause / solution idea / dependencies / testing impact* —
  делает сохранённые решения переиспользуемыми и переносимыми.
- **P5 — Behavior-centric слой + progressive disclosure ($\to$ U5).** Организовать Level 2 вокруг *того,
  что проект делает* (поведения), а не только файлов; выдавать послойно (обзор $\to$ компонент $\to$ юнит) —
  из [[harness_handbook]] (BGPD).
- **P6 — Exploration-eval harness ($\to$ критерии успеха).** Мерить граф как explorer по coverage/ranking
  под line-budget с ground truth из успешных траекторий ([[swe_explore]]) + View-A/B дисциплина
  ([[code_isnt_memory_structural_index]]).
- **P7 — Louvain community detection.** Авто-выделение границ модулей из графа для наполнения Level 2
  (архитектурные конвенции) — приём из [[codebase_memory_tree_sitter_kg]].

## Открытые вопросы

1. ~~Обученный explorer vs training-free tool.~~ **Решено:** HCM — training-free (см. инвариант выше).
   Остаётся не развилка, а *валидационный* замер: насколько training-free путь уступает/не уступает
   обученному explorer'у ([[fastcontext]]) по токенам при равном resolve на одном harness — метрика,
   а не выбор архитектуры.
2. Оптимальная гранулярность единицы памяти: подзадача или полная задача?
3. Как детектировать устаревание кэшированного решения без $\varepsilon$-mutation overhead?
4. Survival value: учитывать «важность» задачи или только частоту? (Редкая, но критическая подзадача не должна вымываться.)
5. Data-flow: насколько реалистично авто-обнаруживать неявные связи через shared storage по коду?
6. Как инкрементально обновлять граф при больших рефакторингах без полного rebuild?
