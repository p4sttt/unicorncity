## 1. Текущее положение дел

Как coding-агент сейчас представляет себе большую кодовую базу, когда получает задачу:

- **Agentic grep + read** — ripgrep-петля по рабочей копии + чтение файлов (OpenCode, Claude Code, Mini-SWE-Agent).
- **RAG по коду** — извлечение семантически близких чанков через эмбеддинги.
- **Временные текстовые заметки / scratchpad** — агент записывает найденное в контекст на время сессии.
- **Repo-maps** — dependency-ранжированная карта файлов (Aider, PageRank по импортам).
- **Структурные индексы** — semantic + lexical + call-graph, но в основном внутри проприетарных стеков.

Общая черта всех open-source подходов: представление кодовой базы **реконструируется на каждой задаче
заново** и оптимизировано на **recall** (найти всё потенциально релевантное), а не на релевантность.

## 2. Проблема в текущей реализации

Статус-кво страдает от двух системных проблем.

**Токенная неэффективность.** Exploration (поиск и чтение кода) доминирует в токен-бюджете агента. Стандартный подход (codesearch + RAG) минимизирует false negatives, но игнорирует false positives — в контекст попадает избыток деталей реализации, не нужных для текущей задачи. Загрязнённый контекст не только дорог, но и заставляет агента тратить ходы на исправление ложных гипотез.

**Деградация памяти.** Всё, что агент узнал, живёт в плоском тексте и не переживает задачу:
- после изменений в коде заметки устаревают — нет механизма инвалидации;
- плоский текст плохо кодирует структурные и **неявные** связи (модуль A вызывает B; оба пишут в таблицу C — явной связи по коду нет, но она есть);
- успешные стратегии прошлых задач не переиспользуются — повторяющиеся подзадачи решаются с нуля.

**Уточнение из литературы 2026** (подробно в [[evidence]]): file-level локализация современными методами уже фактически «решена» — реальное горло сместилось на **line-level coverage и ranking**. Кроме того, локация *без диагноза* (файл без гипотезы о причине) недоспецифицирует последующую правку.

## 3. Точки улучшения

Где статус-кво можно улучшить (нумерация используется в §5 и в [[roadmap]]):

- **U1. Единица локализации.** Файл / FQN $\to$ **диапазон строк `(start, end)`**.
- **U2. Retrieval.** Только call-graph $\to$ **гибрид**: semantic (vector) + lexical (BM25) + call-graph.
- **U3. Форма ответа.** Агент оркестрирует множество мелких запросов $\to$ **exploration-facade**, отдающий готовый ранжированный компактный контекст за один вызов.
- **U4. Память решений.** Сырой outcome $\to$ **структурированный диагностический finding** (причина, зависимости, влияние на тесты).
- **U5. Абстракция.** Только implementation-centric (файлы/функции) $\to$ **+ behavior-centric слой** с progressive disclosure (от обзора к деталям по требованию).
- **U6. Устаревание.** Плоские устаревающие заметки $\to$ **детерминированная инкрементальная инвалидация** («инкремент $\equiv$ ребилд»).

## 4. Решение

**HCM (Hierarchical Context Memory)** — локальный **MCP-сервер** поверх versioncontrol-репозитория, дающий агенту персистентную многоуровневую память вместо повторного изучения кодовой базы. Ключевой принцип: все инструменты возвращают **компактный текст** (сигнатуры, FQN, счётчики, диапазоны строк), а не raw-содержимое файлов — здесь и лежит основная токен-экономия.

**Жёсткое ограничение — training-free.** HCM не дообучает и не тренирует никакие модели: вся ценность переносится через структуру (граф, диагностическая память, компактный контекст) и стандартный протокол MCP, а не через веса. Это делает сервер model-agnostic (работает с любым агентом), обновляемым независимо от модели и воспроизводимым без RL/SFT-пайплайна. Обоснование того, что training-free маршрут достигает тех же результатов, что обученные explorer'ы — в [[evidence]].

Три уровня памяти (таксономия эпизодическая/семантическая/экспериенциальная из
[[se_ga_self_evolving_gui_agent]]):

- **Level 1 — граф кодовой базы (структурный контекст).** Персистентный граф из tree-sitter:
  узлы = объявления (классы, методы, функции), рёбра = вызовы / импорты / зависимости. Запросы `interface` (контракты без реализации), `dependents` (что сломается при изменении X), `blast_radius` (граф влияния). Кодовая база доступна как граф-переменная — агент запрашивает её, а не грузит файлы напрямую (аналогия symbolic-доступа из [[recursive_language_models]]).
- **Level 2 — семантический слой (прото).** Семантический поиск по документации → накопленные конвенции, паттерны, архитектурные правила проекта (аналог `M_SEM`).
- **Level 3 — эволюционная память задач (experiential).** Успешные решения как переиспользуемые granular-единицы с **survival-скорингом**: записи в long tail и устаревшие после рефакторинга стратегии вымываются естественно (механика из [[darwinian_memory_system_gui_agents]]).

Инженерная основа: инкрементальное обновление по git-diff (репарсится только изменённое); слоистая («луковичная») архитектура, где **язык = провайдер** при неизменном ядре (первый провайдер — Java). Никаких внешних сервисов: состояние в `.hcm/` в корне целевого репозитория.

## 5. Как решение покрывает проблему и точки улучшения

**Токенную неэффективность** закрывает принцип компактного ответа (сигнатуры/счётчики вместо файлов)
плюс Level 1: структурный вопрос («кто зависит от X?») получает точечный ответ за один запрос вместо
grep-петли. **Деградацию памяти** закрывают персистентность + инкрементальная инвалидация (U6, уже в
MVP: property-тест «инкремент $\equiv$ ребилд») и Level 3 (переиспользование решений). **Неявные связи** —
целевой запрос `data_flow` над графом (писатели/читатели общей таблицы).

Точки улучшения из §3 распределяются так:
- **Уже построено / в MVP:** U6 (инкрементальность), базис U2 (call-graph), базис U3 (компактные ответы `query_graph`).
- **Предложенные расширения** (обоснование — [[evidence]], статус — [[roadmap]]): U1 line-range citations; U2 гибридный retrieval (добавить semantic+lexical к графу); U3 facade-инструмент `explore(issue)`; U4 диагностическая схема записи Level 3; U5 behavior-centric слой + progressive disclosure над Level 2.

Ни один уровень нельзя заменить плоским текстом или разовым codesearch — в этом ядро идеи: давать
агенту **правильный контекст нужного уровня абстракции**, а не «больше контекста».

## 6. Критерии успеха

Числовые гейты (из `IMPLEMENTATION.md` репозитория — пороги ждут финального утверждения):

- **Токен-экономия (главный KPI):** $\ge 30\%$ экономии токенов-до-решения (HCM vs без), без потери качества решения — dogfood-протокол на реальном Java-репозитории.
- **Полнота разрешения вызовов:** $\ge 70\%$ CALLS-рёбер во внутренние узлы на бенчмарк-репозитории.
- **Полнота `dependents`:** recall type-level зависимостей $\ge 90\%$ против ground truth (`jdeps` / IntelliJ).
- **Инвариант инкремента:** property-тест `update()` $\equiv$ `build()` — 100% зелёный.
- **Поиск по докам / памяти:** hit@3 $\ge 80\%$, включая кросс-язычный RU$\to$EN.
- **Латентность:** `update()` $\le 2$ с на $\le 20$ изменённых файлах; `build()` $\le 60$ с на 100k LOC.

Новые оси оценки из литературы (см. [[evidence]], [[repository_exploration_coding_agents]]):

- **Exploration-качество:** coverage / ranking ответов графа под фиксированным line-budget против
  ground truth, выведенного из успешных агентских траекторий (методология [[swe_explore]]).
- **View-B дисциплина:** засчитывать только контекст, который агент реально *использовал*, а не тот,
  что был «показан» (различие View A / View B из [[code_isnt_memory_structural_index]]) — чтобы KPI
  токен-экономии не приписывал заслуги нетронутым подсказкам.
